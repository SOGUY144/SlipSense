# 🚦 Go-Live Gate: สิ่งที่ต้องเคลียร์ก่อนพิมพ์ "ลุย Production"

> เอกสารนี้ต่อยอดจาก `migration-test-results-and-go-live-checklist.md` — สคริปต์ผ่านการทดสอบ boundary/race condition มาแล้ว (เนื้อหาทางเทคนิคพร้อม) แต่กระบวนการก่อน deploy จริงยังมี 2 จุดที่ต้องเคลียร์ก่อน ห้ามข้ามขั้นตอนนี้

---

## 🚨 จุดที่ 1: ต้องพิสูจน์ว่า Cleanup สำเร็จจริง ไม่ใช่แค่เชื่อคำอธิบาย

ผลลัพธ์ cleanup ที่ได้มา:
```
Deleted 0 test rows (TX1, TX2)  // (ถูกลบไปตั้งแต่ตอนจบทดสอบแล้ว)
Restored 46 existing rows to is_vat_registered = true
Total rows: 46
```

**ปัญหา:** ข้อความ "ถูกลบไปแล้วตอนจบทดสอบ" เป็นแค่คำอธิบาย ไม่ใช่หลักฐาน เราไม่รู้ว่า "0 แถว" นี้แปลว่า:
- (ก) TX1/TX2 ถูกลบไปแล้วจริงๆ ตั้งแต่ก่อนหน้า → ปลอดภัย หรือ
- (ข) สคริปต์ cleanup ใช้เงื่อนไข query ผิดจนหา TX1/TX2 ไม่เจอ → อาจมีข้อมูลปลอมค้างอยู่โดยไม่รู้ตัว

**สิ่งที่ต้องขอก่อนไปต่อ:**
- [ ] ขอ query ยืนยันตรงๆ ว่าไม่มี TX1/TX2 ค้างจริง เช่น:
  ```sql
  SELECT * FROM transactions WHERE id IN ('<TX1 id>', '<TX2 id>');
  -- ต้องได้ 0 แถว
  ```
- [ ] ขอดูโค้ดว่าตอนจบการทดสอบรอบก่อน มีขั้นตอนลบ TX1/TX2 ไว้ตรงไหน (ถ้าไม่มีเลย แปลว่าคำอธิบายที่ให้มาไม่สอดคล้องกับสิ่งที่ทำจริง ต้องสอบถามเพิ่ม)

---

## 🚨 จุดที่ 2: ห้ามให้ AI เป็นคนรันสคริปต์บน Production เอง

**ข้อเสนอที่ได้รับ:** "พิมพ์ว่า 'ลุย Production ได้เลย' แล้ว AI จะรันสคริปต์ 4 ขั้นตอนให้เองผ่าน Terminal"

**เหตุผลที่ไม่ควรทำแบบนี้:**
1. ถ้า AI รันผ่าน terminal ของ session แชทโดยตรง จะไม่มี "จุดหยุดตรวจสอบ" ระหว่างขั้นตอนจริง — ถ้า error เกิดกลางคันบน production จริง จะแก้สถานการณ์ยากกว่าที่ควรจะเป็น
2. งานที่แตะข้อมูลภาษี/การเงินจริงของลูกค้า ควรมีคนจริงในทีมเป็นคนกด run เอง หรือผ่าน CI/CD pipeline ที่มี manual approval step แยกต่างหาก ไม่ใช่ปล่อยให้ AI ตัดสินใจกดรันเองแค่เพราะพิมพ์ประโยคยืนยันสั้นๆ ในแชท

**สิ่งที่ต้องทำแทน:**
- ส่งไฟล์สคริปต์ทั้ง 4 ไฟล์ (`step1-snapshot.ts` ถึง `step4-verify.ts`) ให้ทีม engineer เป็นคนรันเองบน production โดยตรง
- หรือนำเข้า CI/CD pipeline ที่มี manual approval step คั่นก่อนรันจริง

---

## ✅ Checklist สุดท้ายก่อนพิมพ์ "ลุย" (ให้คนในทีมทำเอง ไม่ใช่ AI)

- [ ] ยืนยันด้วย query จริงว่าไม่มี TX1/TX2 ค้างอยู่ในฐานข้อมูล (ตามจุดที่ 1)
- [ ] Backup production database เสร็จแล้วจริง มีไฟล์/snapshot ID ยืนยันชัดเจน
- [ ] คนในทีม (ไม่ใช่ AI) เป็นคนรันสคริปต์ทั้ง 4 ตัวบน production เอง หรือผ่าน CI/CD ที่มี approval step
- [ ] มีแผน rollback ชัดเจน ถ้าขั้นตอนไหนล้มเหลวกลางคัน (เช่น restore จาก backup ทันที)
- [ ] เลือกช่วง off-peak แล้ว และมีคน monitor สดระหว่างรันจริง
- [ ] รัน step4 verify หลังรันจริงเสร็จ แนบผลลัพธ์จริง (จำนวนแถวอัปเดต, จำนวนแถวหลุด — ต้องเป็น 0, เนื้อหาไฟล์ audit log) มาปิดงาน

---

## สรุป

**เนื้อหาทางเทคนิคพร้อมแล้ว** — สคริปต์ผ่านการทดสอบ boundary case และ race condition มาอย่างละเอียด ไม่มีปัญหา precision loss อีกต่อไป

**แต่กระบวนการ deploy ยังขาด 2 อย่าง:** (1) หลักฐานยืนยัน cleanup สำเร็จจริง และ (2) ต้องให้คนในทีมเป็นคนรันบน production เอง ไม่ใช่ AI

**ห้ามพิมพ์ "ลุย Production" จนกว่าจะติ๊กครบทุกข้อใน Checklist ข้างต้น**
