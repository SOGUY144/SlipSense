# Code Review & แผนแก้ไข: ระบบ Tax Report Export (SlipSense)

> เอกสารนี้สรุปจุดที่ต้องแก้ไข/เพิ่มเติมในระบบ export รายงานภาษี (PDF/Excel) เพื่อให้ AI หรือทีมพัฒนานำไปดำเนินการต่อ เรียงตามความสำคัญ

---

## 1. [Critical] แก้ปัญหาการปัดเศษ VAT ไม่ลงตัว (Reconciliation)

**ปัญหาปัจจุบัน:**
```javascript
const total = parseFloat(tx.amount);
const subtotal = total / 1.07;
const tax = total - subtotal;
```
เมื่อมีหลายรายการ ผลรวมของ `subtotal + tax` ต่อแถว อาจไม่เท่ากับผลรวม `total` ทั้งหมด เนื่องจากทศนิยมสะสม (floating point / rounding error)

**สิ่งที่ต้องแก้:**
1. ปัดเศษ `subtotal` และ `tax` เป็น 2 ตำแหน่งทศนิยมเสมอ ก่อนบันทึก/แสดงผล
   ```javascript
   const subtotal = Math.round((total / 1.07) * 100) / 100;
   const tax = Math.round((total - subtotal) * 100) / 100;
   ```
2. เพิ่มฟังก์ชัน **reconciliation check** ท้ายรายงาน:
   - รวมยอด `subtotal` ทุกแถว + รวมยอด `tax` ทุกแถว ต้อง = รวมยอด `total` ทุกแถว แบบเป๊ะ
   - ถ้าผลรวมไม่ตรง (เกิดจากการปัดเศษสะสม) ให้ปรับส่วนต่างสตางค์ที่แถวสุดท้ายของรายงาน (วิธีมาตรฐานที่ซอฟต์แวร์บัญชีใช้)
3. เขียน unit test สำหรับกรณีนี้โดยเฉพาะ (เช่น สุ่มสร้าง 100-1000 รายการ แล้วเช็คผลรวม)

## 2. [Critical] ข้อมูลไม่ครบตามฟอร์แมตรายงานภาษีซื้อ-ขายจริงของกรมสรรพากร

รายงานที่จะใช้ยื่นภาษีจริง ต้องมีคอลัมน์เหล่านี้ ซึ่งระบบปัจจุบันยังไม่มี:

| คอลัมน์ที่ต้องเพิ่ม | หมายเหตุ |
|---|---|
| เลขประจำตัวผู้เสียภาษี 13 หลักของคู่ค้า | ต้องมีช่องกรอก/แก้ไขได้ เพราะสลิปโอนเงินไม่มีข้อมูลนี้ |
| เลขที่ใบกำกับภาษี | แยกจากเลขอ้างอิงธุรกรรม |
| วันที่ในใบกำกับภาษี | อาจไม่ตรงกับวันที่โอนเงิน |
| ชื่อ-ที่อยู่คู่ค้า | สำหรับอ้างอิงในรายงาน |
| Flag "คู่ค้าจด VAT หรือไม่" | ดูข้อ 3 |

**Action:**
- เพิ่ม field เหล่านี้ในโมเดลข้อมูลธุรกรรม (database schema)
- เพิ่ม UI ให้ผู้ใช้กรอก/แก้ไขข้อมูลนี้ก่อนกด export (เพราะข้อมูลจากสลิปอย่างเดียวไม่พอ)
- ถ้าข้อมูลไม่ครบ ให้ระบบ warning ชัดเจนว่า "รายงานนี้เป็นข้อมูลอ้างอิงเบื้องต้น ยังไม่สามารถใช้ยื่นภาษีจริงได้" จนกว่าจะกรอกครบ

## 3. [High] ไม่ใช่ทุกยอดเงินควรถอด VAT อัตโนมัติ

**ปัญหา:** ระบบถอด VAT 7% จากทุกยอดเงินแบบอัตโนมัติ แต่ในความเป็นจริง:
- คู่ค้าที่ไม่ได้จดทะเบียน VAT (บุคคลธรรมดา/ร้านเล็ก) ไม่มีภาษีมูลค่าเพิ่ม
- สินค้า/บริการบางประเภทได้รับยกเว้นภาษี

**สิ่งที่ต้องแก้:**
- เพิ่ม field `isVatRegistered: boolean` ต่อคู่ค้า/ธุรกรรม
- ถ้า `isVatRegistered = false` → `subtotal = total`, `tax = 0` (ไม่ถอด VAT)
- ถ้า `isVatRegistered = true` → ใช้สูตรเดิม (ตามข้อ 1 ที่แก้ rounding แล้ว)
- ตั้งค่า default ให้ผู้ใช้เลือกตอนตั้งค่าคู่ค้าครั้งแรก ไม่ควรเดาอัตโนมัติ

---

## 4. [Medium] เพิ่มฟีเจอร์ภาษีหัก ณ ที่จ่าย (Withholding Tax)

ธุรกิจ SME ไทยส่วนใหญ่ต้องจัดการ WHT คู่กับ VAT (เช่น ค่าบริการหัก 3%, ค่าเช่าหัก 5% เป็นต้น)

**Action (ฟีเจอร์ใหม่ ไม่เร่งด่วนเท่าข้อ 1-3):**
- เพิ่มโมเดลข้อมูล WHT rate ต่อประเภทธุรกรรม
- เพิ่มรายงานแยก หรือคอลัมน์เพิ่มในรายงานเดิม สำหรับยอดหัก ณ ที่จ่าย

---

## 5. [Medium] Performance ฝั่ง Client สำหรับ PDF

**ปัญหา:**
- ฟอนต์ Sarabun แบบ Base64 เต็มตัวฝังในโค้ด ทำให้ bundle size ใหญ่เกินจำเป็น
- ถ้า export ข้อมูลจำนวนมาก (เช่นทั้งปี) การ render ฝั่ง client อาจทำให้ browser ค้าง

**สิ่งที่ต้องแก้:**
- ทำ **font subsetting**: ตัดฟอนต์ Sarabun ให้เหลือเฉพาะตัวอักษรที่ใช้จริง (ใช้เครื่องมือเช่น `fonttools subset` หรือ `glyphhanger`) เพื่อลดขนาดไฟล์
- ถ้าจำนวนแถวเกิน threshold ที่กำหนด (เช่น > 500 แถว) ให้พิจารณา:
  - แบ่งหน้า/แบ่ง batch การ render
  - ย้ายการคำนวณ/จัดรูปแบบข้อมูลไปทำใน Web Worker แยกจาก main thread

---

## 6. [Low] Audit Trail และการเก็บหลักฐาน

กฎหมายไทยกำหนดให้เก็บเอกสารทางบัญชีอย่างน้อย 5 ปี

**สิ่งที่ควรเพิ่ม:**
- Log ทุกครั้งที่มีการ export รายงาน: ใคร, export อะไร, ช่วงเวลาไหน, เมื่อไหร่
- พิจารณาใส่ timestamp หรือ hash ลงในตัวไฟล์ที่ export เพื่อใช้ยืนยันความถูกต้องย้อนหลังได้

---

## สรุปลำดับความสำคัญ

1. แก้ rounding + reconciliation ของ VAT (ข้อ 1) — กระทบความถูกต้องของตัวเลขโดยตรง
2. เพิ่มฟิลด์ข้อมูลให้ตรงฟอร์แมตสรรพากร (ข้อ 2) — ไม่งั้นเอาไปยื่นจริงไม่ได้
3. แก้ logic การถอด VAT ให้ยืดหยุ่นตามสถานะคู่ค้า (ข้อ 3)
4. ฟีเจอร์ WHT (ข้อ 4) — เพิ่มทีหลังได้
5. ปรับปรุง performance ฝั่ง client (ข้อ 5)
6. เพิ่ม audit trail (ข้อ 6)
